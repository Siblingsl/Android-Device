# 授权服务边界加固设计

**日期：** 2026-09-17  
**范围：** `authorization-service` 的监听边界、受保护 HTTP 响应与临时 artifact transfer 状态

## 目标

让服务端交付链在部署到反向代理后仍保持明确的敏感数据边界，并限制未完成下载造成的内存状态增长。

## 设计

### 1. 敏感响应禁止缓存

授权服务的 `/v1/*` 响应统一添加：

- `Cache-Control: no-store`
- `Pragma: no-cache`

服务端不依赖代理正确识别 JSON 内容来决定是否缓存租约、签名 manifest 或加密分块。该策略不记录 token，也不改变普通错误码。

### 2. transfer 状态上限

每个服务进程的临时 transfer map 使用固定上限 `128`：

- 插入新 transfer 前先删除已过期条目；
- 达到上限时返回 `503 transfer_capacity_exhausted`，不读取 artifact、不创建新的密钥材料；
- 读取 chunk 时继续做过期回收；
- 上限只保护服务进程内存，不改变租约、撤销和完整性校验规则。

本地测试允许注入更小上限，以便在不创建 128 个真实文件传输的情况下验证拒绝路径。

### 3. 监听边界默认 fail-closed

授权服务直接提供的是明文 HTTP，TLS 由同机的受管反向代理终止。因此服务进程的
`RDC_AUTH_BIND` 必须解析为字面量回环地址（IPv4 `127.0.0.0/8` 或 IPv6 `::1`）；
通配地址、局域网地址、公网地址和无法解析的主机名均在绑定前拒绝。这样即使部署环境
误把监听地址改成 `0.0.0.0`，也不会把租约或加密分块接口直接暴露在网络上。

生产部署通过同机反向代理访问回环地址并在边缘强制 TLS 1.3；不提供明文公网监听的
开发/生产旁路开关。若未来需要跨容器部署，应增加经过单独评审的内部 TLS 或 Unix
socket 方案，而不是放宽当前校验。

### 4. 请求体上限

`/v1/*` 只接受小型 JSON 控制请求；artifact 内容走已加密的分块响应，不通过
请求体上传。因此路由统一设置 `64 KiB` 请求体上限：

- 超过上限的请求在 JSON 解析和业务逻辑前被拒绝；
- 不读取数据库、artifact 文件或创建 transfer；
- 上限只约束控制面请求，不改变分块下载大小；
- 客户端请求模型保持现状，避免为了通过限制而把敏感数据拆成更多请求。

## 非目标

- 不在客户端保存服务端私钥；
- 不将临时明文交付改为永久缓存；
- 不把服务端部署 TLS 伪装成应用内 TLS；TLS 仍由生产边缘或反向代理终止并强制 TLS 1.3；
- 不对运行中的 QEMU 或 Android 实例做任何改动。

## 验收

- 路由测试确认租约响应含 `no-store`；
- 路由测试确认达到注入上限时返回 503，未创建 transfer；
- 过期 transfer 可被后续 prepare 清理；
- 服务启动配置测试确认仅接受字面量回环监听地址；
- 路由测试确认超过 `64 KiB` 的控制面请求返回 `413`，且不进入业务处理；
- `cargo test --manifest-path authorization-service/Cargo.toml` 与项目四项基线验证通过。
