# 设备状态看板 UI 设计规格

日期：2026-09-09  
状态：已确认，进入分阶段实施

## 1. 产品对象与设计目标

产品对象是 Windows 桌面端的 Redroid / Android 设备运维中心，主要用户需要同时管理多台设备、快速判断异常、打开独立 scrcpy 窗口，并在必要时进入完整的设备详情能力。

本次 UI 的单一首要任务是：让用户在打开应用后，先看清“哪些设备在线、哪些需要处理、当前有什么后台活动”，再用最短路径进入投屏、控制、文件、应用、日志和基础设施工具。

## 2. 已确认的结构

主窗口采用“状态看板 + 活动抽屉 + 工具启动器”结构，不在主窗口内放置伪实时手机画面：

```text
┌────────────────────────────────────────────────────────────────────┐
│ Redroid Device Center   工作区/搜索       状态摘要   工具   设置    │
├────────────────────────────────────────────────────────────────────┤
│ 在线运行                         待授权                  离线/异常  │
│ ┌────────设备卡────────┐         ┌────设备卡────┐        ┌──卡片──┐  │
│ │ 状态 / 资源 / 备注   │         │ 授权提示     │        │ 原因   │  │
│ │ 镜像 控制 文件 应用 │         │ 重试 / 详情   │        │ 处理   │  │
│ └─────────────────────┘         └──────────────┘        └────────┘  │
│                                                                      │
│ 活动抽屉：监控 · 批量任务 · 运行日志 · 告警提示                     │
└────────────────────────────────────────────────────────────────────┘
                                      ┌──────────────────────────────┐
                                      │ 独立原生 scrcpy 窗口          │
                                      │ 由系统窗口管理，不嵌入 WebView │
                                      └──────────────────────────────┘
```

### 2.1 主窗口边界

- 顶部工作区栏替代原来的大侧栏；所有旧页面通过“工具”启动器和上下文入口继续可达。
- 设备卡是主要信息单元，默认紧凑；卡内只放高频行内操作，低频操作放入“更多”。
- 鼠标悬停设备卡显示设备信息卡；点击设备名称或“详情”仍进入原有设备详情页。
- 底部活动抽屉统一承载当前状态文本、进度、图表、批量结果、日志和告警入口，不删除现有反馈内容。
- scrcpy 永远以独立原生窗口打开；主窗口只显示启动状态、窗口状态和重新打开入口。
- 不复制 escrcpy 的表格、顶部标签或底部连接条布局；本项目使用状态分栏和活动抽屉作为独立识别点。

### 2.2 视觉方向

- 背景：`#f6f7f9`；卡片：`#ffffff`；文字：`#17202f`；次级文字：`#718096`。
- 主强调色：`#0e9f94`，用于在线、可执行和已完成状态。
- 风险色：`#e2a23a`，用于待授权、等待和资源预警。
- 错误色：`#dc5c5c`，只用于失败、离线和危险动作。
- 数据色：`#4f7cac`，用于监控曲线和诊断信息。
- 保留深色主题，但由同一组语义色映射，不为深色主题引入另一套布局。
- 字体继续优先使用系统字体，数据和 Serial 使用等宽字体；通过细分字重、短标签和留白建立层次，不依赖大面积渐变或装饰卡片。
- 视觉签名是“状态泳道 + 独立窗口边界”：主窗口表示管理面，scrcpy 表示设备实时面，两个职责不混淆。

## 3. 兼容要求

- 不删除或改名现有 Tauri 命令、服务方法、设置字段和存储键。
- Dashboard、设备中心、设备详情、Docker、ADB、APK、文件、Volumes、Logcat、监控告警、系统日志、设置和 Root 入口都必须继续可达。
- 现有截图轮询、鼠标点击/拖动/滚轮/右键/中键、独立 scrcpy、设备控制、Shell、应用管理、文件传输、批量结果、监控图表和告警撤销都必须保留。
- 现有中文/英文文案和失败反馈语义继续保留；新入口补齐双语文案。
- 参考目录 `Reference_Projects/escrcpy` 只用于对照，不参与主项目构建和测试，不修改其中任何文件。
- 不为尚未具备后端能力的指标伪造实时数据；后端暂时没有返回的电量、温度、电压等字段显示为“未提供”，并保留未来接入位置。

## 4. 功能迁移规则

| 现有能力 | 新入口 | 兼容处理 |
|---|---|---|
| 设备刷新、搜索、筛选、多选 | 顶部工作区栏 + 看板工具条 | 保留原 session 持久化键和设备中心完整页 |
| 连接、断开、重启、停止、亮屏、锁屏、HOME、BACK、RECENT | 设备卡行内操作 / 更多 | 继续复用 `DeviceService` 和原确认逻辑 |
| 截图预览与鼠标操作 | 详情页控制区 | 主看板仅展示最近截图状态，不宣称实时视频 |
| scrcpy 启动、停止、重连 | 设备卡“镜像” | 继续调用外部进程；显示独立窗口状态 |
| 文件、应用、Shell、Logcat、Root | 工具启动器 + 设备卡上下文 | 原完整页面不移除，未来逐步做上下文面板 |
| 监控图表、告警、批量进度、状态栏 | 底部活动抽屉 | 保留原 `/monitor`、`/logs` 和结果页作为深入口 |
| Docker、ADB、APK、Volumes、Settings | 工具启动器 | 保留原路由和页面行为 |

## 5. 对照缺口的实施边界

用户列出的缺口按 P0、P1、P2 建立后续实现清单。第一阶段不假装这些能力已经实现，而是先保证它们在信息架构中有稳定承载位置：

- P0：紧凑设备列表、悬浮信息卡、紧凑控制栏、录制、音量/旋转/电源、文件管理细节、无线调试配对、mDNS、批量镜像/推送/多 APK、多设备广播输入。
- P1：设备备注、历史离线设备、控制栏排序持久化、浮动控制窗口、摄像头参数、OTG、应用快速选择器、文件收藏/最近路径、无线地址批量重连、多设备布局。
- P2：可视化 scrcpy 参数、全局快捷键、更新中心和文档入口。

每个能力必须遵循“入口 → 操作 → 进行中/成功/失败反馈 → 可回看或跳转”的闭环；如果平台或 scrcpy 版本不支持，界面必须显示真实原因，不提供无效按钮。

## 6. 验收标准

1. 主窗口使用已确认的状态看板结构，不再依赖大侧栏和大面积主预览。
2. 用户可以从主窗口直接打开独立 scrcpy，主窗口不会嵌入或模拟视频流。
3. 所有当前页面路由、设备详情能力、图表、提示、日志、批量结果和错误反馈均可通过新入口到达。
4. 设备卡在宽度受限时仍能显示状态和高频操作；低频动作不挤压卡片。
5. 缺失后端指标不显示虚假数值；未完成的未来能力有清晰的不可用原因或后续接入位。
6. 中文、英文、浅色、深色主题均可构建；原项目测试不因参考目录而被污染。
