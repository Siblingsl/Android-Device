# Redroid Device Center 开源 Beta 产品化设计

**日期**：2026-09-16
**状态**：待实施
**目标版本**：Windows x64 技术 Beta
**设计范围**：安装、依赖、文档与演示、发布工程、社区协作、真机 QA

## 1. 目标与产品边界

Redroid Device Center 的首个公开版本定位为：

> 面向 Android 自动化开发、云手机控制和 App 测试团队的 Windows x64 技术 Beta。

项目当前已经具备较强的核心能力：Docker 轨道、QEMU/WHPX 轨道、ADB/scrcpy 控制、Root/GApps 等预装，以及跨轨对比页面。当前短板不是继续堆功能，而是把这些能力变成陌生用户可安装、可理解、可复现、可反馈的产品。

### 1.1 成功标准

公开 Beta 必须能够证明：

1. 用户在干净 Windows x64 机器上可以按文档安装并启动。
2. 首次使用时能清楚知道 Docker、WSL2/binder、ADB、scrcpy、QEMU、WHPX、镜像、GApps 和 ABI 的状态。
3. 用户不需要阅读源码来判断失败原因，也不需要猜下一步操作。
4. 至少一条轨道可以稳定完成“创建首台 Android 设备 → ADB 连接 → 基本操作”。
5. 不支持的组合有明确原因，不以空值或伪造的 0 显示为可用。
6. 每个公开版本都有可验证的构建产物、测试记录、校验和、变更说明和回滚方式。
7. 真机人工走查后的视觉、导航、键盘操作和无障碍结果有证据，不由自动化测试冒充人工验收。

### 1.2 首版明确不承诺

- 不把 macOS 作为首个 Beta 的正式支持平台。现有 macOS 打包工作流必须标为实验性，不能出现在“受支持平台”的默认路径中。
- 不承诺 Windows ARM64 的稳定支持；相关内核资产可以保留为实验性资产，但必须在矩阵中单独标明。
- 不把 Docker Desktop、Android 镜像或 GApps 强制打进安装包。
- 不绕过 WHPX、binder、ABI 或 GApps 版本限制来制造“看起来支持”。
- 不在没有显式授权的情况下修改 `src-tauri` 或 `qemu-center` 的后端行为。

## 2. 设计原则

### 2.1 先建立信任，再降低摩擦

先让文档、支持边界、构建和问题反馈可信，再增加应用内自动引导。用户遇到失败时，产品应明确说明“缺什么”和“为什么”，而不是隐藏限制。

### 2.2 两条轨道保持诚实分离

Docker 和 QEMU/WHPX 是不同的运行时边界、依赖组合和故障模型。页面可以统一入口，但安装、体检、排障和兼容性矩阵必须按轨道分别表达。

### 2.3 优先复用已有能力

优先复用现有的 `doctor`、QEMU CLI、Docker 检查、ADB 状态、路径检测、日志落盘和页面合并结果，不再建立第二套平行检测逻辑。

### 2.4 数据缺失必须可见

指标、健康度和兼容性状态不得用默认 0 或模糊的“正常”替代缺失数据。所有状态至少区分“可用”“需要处理”“不支持/无数据”。

### 2.5 每一阶段都有独立验收门

一个阶段完成后必须通过既定检查并形成提交；后续阶段不得把未验证的实验性能力包装成稳定能力。

## 3. 工作包与依赖关系

| 顺序 | 工作包 | 主要产物 | 后端改动 | 依赖 |
|---|---|---|---|---|
| 0 | 合并尾项 | P7-1 真机走查记录、问题清单 | 否 | 当前 node1、Docker 环境 |
| 1 | 开源基础 | 文档、兼容性矩阵、社区规范、PR CI | 否 | 无 |
| 2 | 真实 QA | 干净 Windows 记录、截图、视频、排障案例 | 否 | 工作包 1 的文档 |
| 3 | 首次启动引导 | 应用内环境准备度与修复入口 | 是，需要单独授权 | 工作包 1、现有检测能力 |
| 4 | Beta 发布 | Windows 包、校验和、发布说明、签名/升级门 | 配置为主 | 工作包 1、2；正式签名依赖证书 |

工作包 0 是当前合并工作的收尾；工作包 1 可以立即开始；工作包 3 明确后置，避免在产品边界尚未固定时修改后端契约。

## 4. 工作包 0：关闭页面合并尾项

### 4.1 任务

- 使用外部清单 `2026-09-16-merge-p7-walkthrough-checklist.md` 完成 C / D / E 三节人工走查。
- 将清单复制到仓库 `docs/qa/2026-09-16-merge-p7-walkthrough-checklist.md`，让验收证据随代码版本保存。
- 记录页面导航、两条轨道的核心功能、错误状态、视觉细节、键盘导航和 a11y 结果。
- 每个发现的问题都进入修复提交或可追踪 Issue。

### 4.2 验收门

- C / D / E 每项都有“通过 / 不通过 / 未执行”结果和备注。
- 不把浏览器预览、DOM 断言或自动化测试当作真机视觉通过证据。
- P7-1 完成后，合并页是否完成可以由清单和提交记录复核。

## 5. 工作包 1：开源 Beta 基础

### 5.1 文档结构

新增或整理以下入口，文件名可在实施阶段根据现有文档合并，避免重复维护：

```text
README.md
CONTRIBUTING.md
SECURITY.md
CHANGELOG.md
docs/
  getting-started/
    windows-clean.md
    docker-track.md
    qemu-whpx-track.md
  compatibility.md
  troubleshooting.md
  qa/
    2026-09-16-merge-p7-walkthrough-checklist.md
    clean-windows-beta-checklist.md
  release-checklist.md
```

### 5.2 README 的首屏结构

README 首屏只回答四件事：

1. 这是什么，适合谁。
2. 当前 Beta 支持什么平台和轨道。
3. 新用户应该选择 Docker 还是 QEMU/WHPX。
4. 如何进入“首台设备成功”路径。

现有 README 中较深的 Root、局域网扫描、Binder 内核和开发细节继续保留，但移动到分层文档或章节末尾；不能让第一次打开 README 的用户先面对所有高级能力。

### 5.3 安装文档的统一模板

每条安装路径使用同一结构：

- 适用环境。
- 必须准备的依赖。
- 安装/启动步骤。
- 每一步的成功标志。
- 首台设备操作。
- 常见失败与恢复。
- 日志和 Issue 信息收集方式。

文档必须明确哪些步骤需要管理员权限、重启或下载大文件；不能把这些成本隐藏到“运行一下即可”。

### 5.4 兼容性矩阵

矩阵以“已验证 / 理论可行 / 实验性 / 不支持”区分，而不是只列一个宽泛的 supported：

| 维度 | 至少覆盖 |
|---|---|
| Windows | Windows 11 x64；Windows 10 x64（若未验证则标未验证） |
| CPU/虚拟化 | Intel/AMD、WHPX、虚拟化开关、磁盘空间 |
| Docker 轨 | Docker Desktop、WSL2、binder 内核、Docker 引擎 |
| QEMU 轨 | WHPX、QEMU、OpenSSH、Ubuntu cloud image |
| 工具 | ADB、scrcpy、QEMU 二进制 |
| Android | Android 13/14、x86_64、设备档案 |
| 可选能力 | GApps、Magisk/Zygisk、LSPosed、Shamiko、Cloak |
| 发布包 | Windows x64 安装包；macOS/ARM64 单独标实验性 |

矩阵中的每一个“已验证”都必须链接到测试记录、命令输出或真机走查证据。

### 5.5 社区入口

- `CONTRIBUTING.md`：开发环境、分支和提交约定、测试命令、前后端授权边界、如何提交文档和测试改进。
- `SECURITY.md`：不要公开提交密钥、设备日志和敏感配置；安全问题私下报告；Root/隐藏能力仅限授权测试。
- `CHANGELOG.md`：按版本记录新增、修复、限制和升级注意事项。
- Issue 模板：Bug、安装/环境问题、功能建议三类，安装/环境问题模板必须要求平台、轨道、版本、日志和复现步骤。
- PR 模板：变更范围、风险、测试结果、是否涉及后端、是否需要真机验收。

## 6. 工作包 2：真实 QA 与演示资产

### 6.1 干净 Windows 验收

使用没有 Node、Rust、Docker、ADB 和 QEMU 开发环境的 Windows x64 机器，记录从下载到首台设备连接的完整过程。

验收至少覆盖：

1. 安装包安装、启动和卸载。
2. Docker 轨首台设备。
3. QEMU/WHPX 轨首台设备。
4. ADB 连接和 scrcpy/基本控制。
5. Android 13 GApps 路径和 Android 14 不兼容提示。
6. Root 预装及已知模块限制。
7. 升级、数据保留、失败回滚和重新启动。
8. 依赖缺失时的提示和恢复。

### 6.2 演示视频

只制作一条主视频，时长控制在 3–5 分钟：

- 展示项目定位。
- 从环境检查进入 Docker 或 QEMU。
- 创建设备并连接。
- 展示设备控制。
- 展示一个可选能力。
- 展示失败时的清晰提示。

高级 Root/GApps 全流程可以作为补充短视频，不把主视频做成所有能力的堆叠。

### 6.3 视觉与无障碍证据

人工走查记录：

- 侧边栏与合并页入口。
- 轨道切换和 URL 可恢复性。
- 加载、空数据、失败和不可用状态。
- 键盘 Tab 顺序、焦点可见性和快捷导航。
- 文本对比度、按钮禁用态、图标辨识度。
- 中文/英文切换后的布局和文案截断。

## 7. 工作包 3：首次启动环境引导

这是唯一需要单独取得后端改动授权的主要工作包。

### 7.1 复用边界

- 复用 QEMU `doctor --json` 和现有 Docker/ADB/路径检查。
- 前端消费结构化快照，不在页面外壳或对比视图里发服务调用和定时器。
- 检测结果必须携带状态、原因、轨道、版本/路径信息和建议动作。
- “修复”动作首版优先打开官方入口、显示安装说明或复制安全命令，不默认自动修改系统。

### 7.2 依赖状态模型

统一使用以下语义：

- `ready`：当前轨道可使用。
- `action_required`：可以解释并引导修复。
- `unsupported`：组合本身不支持，不能通过安装依赖解决。
- `unknown`：检查未完成或数据源不可用。

禁止用 `0`、空字符串或普通绿色徽标表示 `unknown`。

### 7.3 首台设备路径

将“无 GApps 基础 Redroid”作为最快成功路径；GApps、Root、LSPosed、Shamiko、设备伪装作为经过版本和 ABI 检查的可选路径。这样新用户可以先验证运行环境，再决定是否承担高级预装的额外限制。

## 8. 工作包 4：Beta 发布工程

### 8.1 CI 分层

现有 `.github/workflows/quality.yml` 作为 PR 质量门，补齐：

- TypeScript 检查。
- Vitest 全量测试。
- `src-tauri` Rust 测试。
- `qemu-center` Rust 测试。
- 前端构建。
- 锁文件安装和依赖审计。

发布工作流单独负责 Windows x64：

- 仅 tag 或手动触发。
- 固定 Node/Rust 工具链。
- 构建 NSIS 安装包。
- 校验安装包存在、版本匹配并生成 SHA-256。
- 上传安装包、校验文件和发布元数据。
- 运行失败时不得产生“看起来完整”的 Release。

现有 macOS 工作流不能与 Windows Beta 的支持声明混用；在矩阵和发布说明中标为实验性，或暂时从正式发布工作流中移出。

### 8.2 签名与升级

按三个门推进：

1. 构建门：CI 稳定生成可安装 Windows 包。
2. 可信门：使用正式证书签名，并在干净机器验证 Windows SmartScreen/安装行为。
3. 升级门：配置 updater endpoint 和公钥，验证升级、取消、失败恢复和旧版本回滚。

在第 2 门完成前，不宣传“已签名”；在第 3 门完成前，不打开默认自动更新。现有 `tauri-release-build.mjs` 的 endpoint/pubkey 强制校验继续保留，并纳入发布验收。

### 8.3 Release Notes 模板

每次 Beta 发布说明固定包含：

- 本版本适合谁。
- 新增与修复。
- 已验证的平台和轨道。
- 已知限制。
- 安装包校验值。
- 升级与回滚方式。
- 如何提交问题。

## 9. 具体阶段与提交拆分

### 阶段 A：文档与协作基础

范围：README、安装指南、兼容性矩阵、排障、贡献规范、Issue/PR 模板、变更记录。

完成标志：陌生开发者可以仅依赖仓库文档搭建开发环境，并知道如何报告安装失败。

### 阶段 B：CI 与 Windows 发布骨架

范围：补齐现有质量工作流，新增 Windows x64 构建/校验/Artifact 工作流，暂不启用正式签名和自动更新。

完成标志：Pull Request 有完整质量门；tag 可以产出可验证安装包。

### 阶段 C：P7-1 真机 QA 与素材

范围：人工走查、干净 Windows 验收、截图、演示视频、兼容性证据。

完成标志：矩阵中的“已验证”都有证据，主 README 不再承诺未验证组合。

### 阶段 D：应用内环境引导

范围：在取得后端授权后实现环境准备度、修复入口和首台设备引导。

完成标志：依赖问题可以在应用内被识别、解释和重新检查；不改变现有两条轨道的核心行为。

### 阶段 E：正式 Beta 发布

范围：正式签名、升级通道、发布说明、反馈闭环。

完成标志：签名、升级和回滚均在干净 Windows 上有实测记录。

每个阶段都单独运行项目规定的四套验证，并使用清晰的阶段提交；视觉和真机阶段额外附人工记录。

## 10. 风险和处理策略

| 风险 | 处理 |
|---|---|
| Docker Desktop、WSL2、WHPX 受系统状态影响 | 应用内明确显示状态；文档标出管理员权限和重启点 |
| GApps 与 Android 版本/ABI 不匹配 | 创建前校验；矩阵列出具体版本；不自动降级或伪装成功 |
| QEMU/WHPX 卡死或磁盘风险 | 保留优雅停止、串口日志、快照边界和恢复说明；不提供硬杀作为常规操作 |
| CI 能构建但发布包缺少资源 | 发布工作流做文件存在性和版本检查，失败即阻断上传 |
| 签名证书泄露 | 只使用 GitHub Secrets，文档禁止提交证书和私钥，发布前做密钥审计 |
| 文档与实际行为漂移 | 每次发布必须复跑安装清单，兼容性矩阵只允许有证据的“已验证” |
| 当前前端偶发测试 flake | 不降低质量门；记录失败用例并单独定位，复跑通过不能抹掉问题记录 |

## 11. 后端授权边界

在用户明确授权前，本设计只允许修改文档、测试流程、CI、发布配置和社区文件。以下事项需要单独确认：

- 修改 `src-tauri` 的依赖检测、环境体检、Docker 指标或安装动作。
- 修改 `qemu-center` 的 doctor、setup、VM、实例或 SSH 行为。
- 实现 P6b 的 CPU/内存/磁盘/启动耗时后端数据源。
- 改变安装包默认资源、系统权限或自动更新行为。

## 12. 最终 Beta 发布门

只有以下证据全部存在，才允许称为“公开 Beta”：

- 干净 Windows x64 安装记录。
- Docker 或 QEMU 至少一条轨道的首台设备成功记录。
- 依赖和兼容性矩阵。
- 故障排查文档和日志收集方式。
- 截图和主演示视频。
- P7-1 真机人工走查记录。
- PR CI 全绿记录。
- Windows 安装包、SHA-256 和 Release Notes。
- 签名与升级状态的诚实说明；未完成的能力不得写成已支持。

这份设计不宣称上述发布门已经完成；它定义下一阶段需要取得的证据和具体交付物。
